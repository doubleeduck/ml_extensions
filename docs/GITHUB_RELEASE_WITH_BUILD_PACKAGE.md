# Подготовка расширений к GitHub Release через build-package.ps1

Этот документ — пошаговая инструкция издателю **единого официального пакета**.
В нём 29 ручных JS-источников с прежними `sourceId`. Обновление атомарное для
всего пакета, но авторизация, cookies, настройки и runtime-контексты источников
остаются отдельными. Старые Dart-парсеры не включаются ни в пакет, ни в production
граф приложения. Приложение и пакет выпускаются независимо.

Инструкция не публикует ничего автоматически. Примеры `OWNER/REPO`, путей,
версии и serial необходимо заменить своими. Лицензия: **«Все права защищены»**.

## 1. Что нужно заранее

- Node.js 22 или новее, доступный командой `node --version`.
- Windows PowerShell 5.1 или PowerShell 7 (`pwsh`).
- Папка официальных расширений: `extensions/official` в этом проекте или корень
  отдельного репозитория с тем же содержимым.
- Собственный Ed25519 private key в PEM/PKCS#8, **вне публикуемой папки**.
- Неизменный `KeyId` для этого ключа, например `official-publisher-2026`.
- Для GitHub: публичный репозиторий `owner/repo`, выбранная версия и растущий
  `IndexSerial`. Приложение сейчас использует публичный Releases API без GitHub
  token; приватный репозиторий через этот flow не поддерживается.

Для одной упаковки не нужны Flutter, Dart, Android SDK, npm-зависимости или
Visual Studio. `build-package.ps1` использует Node built-ins: он **не запускает**
`npm install`, тесты, сборку приложения, загрузку пакета или установку на телефон.
Подготовленный архив проверяется packer-ом до выдачи результата; это не заменяет
тесты источников и приёмку в приложении.

## 2. Подготовить отдельный репозиторий

Корнем будущего репозитория должна стать **папка `extensions/official`**, а не весь
Flutter-проект. Сохранить в ней:

- `src/`: runtime JS и общие engines/helpers без копирования одинакового кода;
- `sdk/`, `templates/`, `tools/`, `tests/`, `docs/`;
- `build-package.ps1`, `package.json`, `package-lock.json`;
- `.github/`, `.gitignore`, `README.md`, `LICENSE`.

Не публиковать `.tmp`, `.keys`, PEM/private keys, локальные cookies/токены,
пользовательские данные, `node_modules`, Flutter build outputs. `dist/` игнорируется:
готовые release-файлы загружаются в GitHub Release, а не коммитятся в исходники.
Перед коммитом проверить `git status --short` и staged diff. `.gitignore` — защита
от случайного добавления, а не гарантия отсутствия секрета в истории Git.

После переноса в самостоятельный репозиторий относительные пути к приложению
меняются: `npm run check:host` предназначен для монорепозитория. Node fixtures и
`npm run build:host` можно запускать из отдельного репозитория. Нативные parity-
и app-тесты выполняются в приложении для соответствующего состояния `src/`.

## 3. Создать или выбрать ключ издателя

Ключ создаётся один раз, не заново для каждого обновления. Пример из корня
приложения, при условии что личная папка доступна только владельцу:

```powershell
node ./extensions/official/tools/pack.mjs --generate-key C:/private/mangalaunch-official.pem --key-id official-publisher-2026
```

В отдельном репозитории путь к команде — `./tools/pack.mjs`. Private PEM нельзя
добавлять в Git, выпускать как asset, передавать пользователям, выводить в логи
или класть в `.mlsource`. Нужна защищённая резервная копия под контролем владельца.
Windows ACL и доступ к резервной копии настраиваются владельцем отдельно.

**Не использовать для публичного релиза** ключи из `.tmp`, детерминированные
test fixtures или development key этого workspace. Генератор дополнительно
пишет `<private-key-path>.public.json`; для установки используйте **полную запись
`*.mlsource.public.json`, созданную упаковкой** — в ней есть namespace пакета.

Ключ и `KeyId` должны оставаться прежними при обычном обновлении. Пакет не может
сам себе выдать доверие: SHA-256 fingerprint публичного ключа проверяется через
отдельный доверенный канал, а пользователь подтверждает издателя в приложении.
Файл public key рядом с архивом сам по себе не доказывает подлинность.

## 4. Подготовить версию и проверить изменения

Версия передаётся параметром `-Version`, например `1.0.0` или `1.1.0-beta.1`.
`package.json.version` не определяет версию `.mlsource`. Использовать SemVer без
префикса `v` и без build metadata (`+...`); prerelease идентификаторы — корректные
SemVer. Тег релиза затем должен быть `v1.0.0` или `v1.1.0-beta.1`.

Каждому изменению опубликованных bytes — новая версия. Нельзя заменить архив
другим содержимым под прежней версией/тегом, изменить старую подпись или молча
поменять source IDs. Сохранить `extensionId = official.mangalaunch.sources` и все
29 прежних `sourceId`: именно они связывают библиотеку, прогресс, историю и загрузки.

Для разработки и приёмки, отдельно от команды упаковки:

```powershell
Set-Location D:/mangalaunch/mangalaunch/extensions/official
npm ci
npm test
npm run check:host
```

После изменений host SDK: `npm run sync:host`, затем тесты приложения и его
сборки. После изменений только JS-парсеров новый Flutter build обычно не нужен,
но поведение нового пакета должно быть проверено в совместимой версии приложения.
Минимальные API/ABI/app-version декларации берутся из `src/definitions.mjs`;
не повышать их без необходимости и не понижать вопреки реально используемым API.

## 5. Подготовить пакет без GitHub-индекса

Из корня приложения:

```powershell
./extensions/official/build-package.ps1 -KeyPath C:/private/mangalaunch-official.pem -KeyId official-publisher-2026 -Version 1.0.0 -OutputPath D:/releases/mlsource/1.0.0/official.mangalaunch.sources.mlsource
```

Из корня самостоятельного репозитория:

```powershell
./build-package.ps1 -KeyPath C:/private/mangalaunch-official.pem -KeyId official-publisher-2026 -Version 1.0.0 -OutputPath D:/releases/mlsource/1.0.0/official.mangalaunch.sources.mlsource
```

Пути с пробелами заключать в кавычки. По умолчанию результат записывается в
`dist/official.mangalaunch.sources.mlsource` и **перезаписывается при следующей
упаковке**. Для хранения релизов использовать отдельный каталог на каждую версию,
как в примере. Это предотвращает путаницу локальных результатов.

Без `-Repository` создаются три файла: архив, публичная запись, checksum. Они
подходят для ручного импорта в приложении. Сборка приложения архив не создаёт.

## 6. Подготовить полный комплект для GitHub

```powershell
./build-package.ps1 -KeyPath C:/private/mangalaunch-official.pem -KeyId official-publisher-2026 -Version 1.0.0 -OutputPath D:/releases/mlsource/1.0.0/official.mangalaunch.sources.mlsource -Repository OWNER/REPO -IndexSerial 1
```

В монорепозитории использовать `./extensions/official/build-package.ps1`.
`Repository` должен соответствовать реальному репозиторию; в подписанном JSON
он нормализуется в lowercase. Один комплект нельзя без переподписи индекса
выдавать за выпуск из другого `owner/repo`.

| Файл | Назначение |
| --- | --- |
| `official.mangalaunch.sources.mlsource` | Подписанный ZIP: manifest, подпись, runtime JS, LICENSE |
| `official.mangalaunch.sources.mlsource.public.json` | Публичный ключ, KeyId, namespace, перечень source IDs |
| `official.mangalaunch.sources.mlsource.sha256` | SHA-256 всего архива для сверки загрузки |
| `extensions-index.json` | Канонический подписываемый индекс: версия, тег, hash, размер, API/ABI, source IDs |
| `extensions-index.ed25519` | Отдельная **бинарная подпись 64 bytes**, не base64 и не текст |

Перед выпуском проверить `$LASTEXITCODE`/отсутствие ошибки скрипта и наличие всех
пяти файлов. Контрольная сумма:

```powershell
Get-FileHash -Algorithm SHA256 D:/releases/mlsource/1.0.0/official.mangalaunch.sources.mlsource
Get-Content D:/releases/mlsource/1.0.0/official.mangalaunch.sources.mlsource.sha256
```

Хэши должны совпасть без учёта регистра. `.sha256` полезен для сверки, но доверие
обеспечивают проверенные Ed25519-подписи, namespace ownership и согласие пользователя.
При тех же исходниках/ключе/версии архив воспроизводим byte-for-byte. Индекс
содержит текущее время, поэтому повторная упаковка может изменить **индекс**.

### Правило IndexSerial

- Положительное целое, увеличивается для каждого **нового опубликованного
  индекса** одного репозитория, включая prerelease и ротацию ключа.
- Не сбрасывать при новом годе/версии, переносе CI или повторном запуске workflow.
- Один serial нельзя использовать для разных bytes. До публикации можно
  пересобирать локально; после публикации меняющиеся метаданные требуют нового serial.
- При смешивании локального выпуска и CI учитывать уже опубликованный максимум.
  В CI сейчас serial вычисляется как `GITHUB_RUN_NUMBER * 100 + GITHUB_RUN_ATTEMPT`;
  он обязан быть выше всех предыдущих. Сам скрипт не запрашивает GitHub и не
  проверяет историю опубликованных serial за издателя.
- Индекс действителен 30 дней; максимум принимаемый приложением — 31 день.
  Перед истечением выпустить свежие метаданные. Простой поддерживаемый путь —
  новая версия пакета/релиз с новым serial, даже если код источников не менялся.
  Уже установленные пакеты не перестают работать из-за истечения индекса.

## 7. Выложить в GitHub вручную

1. Закоммитить принятые исходники в отдельном репозитории. Убедиться, что private
   key и `dist` не попали в staged files или историю.
2. Проверить текущую версию пакета в совместимом приложении, включая import,
   обновление, откат, авторизацию, поиск, главы, media/CDN, скачивание и offline.
   Записать принятый commit и результаты проверок; fixtures не равны live-приёмке.
3. Создать тег `vVERSION` на проверенном commit. Не передвигать существующий тег.
4. В GitHub → Releases создать release для этого тега. Для `-beta`/`-dev` отметить
   prerelease. Описать изменения, минимум версии приложения и важные новые grants.
5. Прикрепить **все пять файлов из одного результата упаковки**. Сохранить точные
   имена, особенно `extensions-index.json` и `extensions-index.ed25519`. Не заменять
   `.mlsource` автоматически создаваемым GitHub архивом `Source code.zip`.
6. Независимо сверить опубликованные размеры/hash; fingerprint ключа разместить
   через доверенный канал. Не прикладывать private PEM или архив личной `.keys`.
7. В MangaLaunch открыть **Настройки → Расширения → GitHub**, указать `OWNER/REPO`
   или ссылку на release, выбрать версию и проверить экран разрешений.

Первое доверие к издателю устанавливается отдельным импортом полного
`.mlsource.public.json` через **Импорт** с проверкой fingerprint. Также можно
выбрать public record и `.mlsource` одновременно: публичные записи обрабатываются
первыми, но всё равно требуют подтверждения. Установка/обновление не автоматические.
Пакет обязан пройти независимую проверку приложения после скачивания.

Отсутствие источников в свежей установке нормально: они не вшиты в APK/exe.
Импорт официального пакета возвращает прежние IDs без миграции пользовательских
ключей. Для каждого источника действует своя сессия, общих cookies не создаётся.

## 8. Альтернатива: защищённый release workflow

Подробности — [BUILD_AND_RELEASE.md](BUILD_AND_RELEASE.md). В самостоятельном
репозитории настроить environment `official-source-release` с обязательным
reviewer, переменные `MLSOURCE_PUBLISHER_KEY_ID`, `ACCEPTED_APP_COMMIT` и secret
`MLSOURCE_SIGNING_KEY_BASE64`. Несмотря на имя, `ACCEPTED_APP_COMMIT` сейчас
проверяется **против commit репозитория расширений**, а не SHA другого репозитория.
Его заполняют после app/native-приёмки именно этого состояния расширений.

Workflow запускается вручную на принятом ref с существующим `vVERSION` tag и
публикует тот же комплект. PR не должен получать signing secret. Не добавлять
новую систему автоматического доверия ключам ради удобства CI.

## 9. Обновление, откат и смена ключа

Обычный выпуск: те же extension/source IDs и key, новая SemVer и новый serial.
Старые release assets оставлять неизменными для явного отката. Приложение хранит
индексные pins: забывание репозитория не снимает защиту от подмены/старого serial.
Пропавшая подпись/просроченный индекс не дают молча перейти на unsigned metadata.

При смене ключа новый `KeyId` импортируется и подтверждается независимо. Переход
издателя пакета и pinned repository key дополнительно подтверждается в UI.
Не менять public bytes под прежним KeyId. Старый ключ отзывать после согласованного
перехода. Отозванный ключ не должен позволять запуск или откат своих пакетов.
Удаление регистрации расширения не должно удалять library/history/downloads/auth;
source ownership сохраняется, чтобы другой namespace не присвоил сохранённую сессию.

## 10. Если что-то не получилось

- **Node не найден:** установить/добавить Node в PATH; скрипт ничего не скачивает.
- **ExecutionPolicy:** использовать разрешённую владельцем PowerShell-сессию;
  не менять глобальные системные ограничения ради упаковки.
- **KeyPath/подпись:** проверить путь, Ed25519/PKCS#8 и соответствие KeyId. Не
  печатать private PEM в лог ради диагностики.
- **Нет доверенного издателя:** импортировать полную публичную запись и сверить
  fingerprint. Не отключать verifier и не добавлять автоматическое доверие ZIP.
- **Нет подходящих релизов:** нужен опубликованный release с uploaded `.mlsource`
  asset; исходники GitHub/tag сами по себе не являются пакетом.
- **Индекс не принят:** проверить repo/tag/serial/срок UTC, бинарную detached
  подпись, пару ключей, hash/размер/IDs. Не редактировать JSON после подписи.
- **GitHub rate limit:** дождаться `retry-after`; постоянные повторы не помогут.
- **Подпись проходит, источник не работает:** это отдельный parser/network/auth
  дефект. Не переупаковывать другие bytes под уже опубликованной версией — исправить,
  проверить и выпустить следующую. Не очищать пользовательские данные для проверки.

Для реализации новых источников разработчиком или ИИ-агентом:
[AUTHORING.md](AUTHORING.md), [source-api.d.ts](../sdk/source-api.d.ts),
[manifest.schema.json](../sdk/manifest.schema.json) и `templates/json-api/`.
